## C0.1: edit fidelity

The script drives the real server over stdio. For each edit it writes a fresh copy of the file, calls `html_edit`,
and reads the file back. html5lib then confirms, for each edit, the ref's tag, that the range holds exactly the
element (the marker check), and whether the splice keeps the tree outside the element.

| Measure | Value |
|---|---|
| Files | 10 (the C0.5 set) + 6 copies of files 8 and 5 (CRLF, BOM, U+1F600 before each `</`) |
| Task edits (text, attribute, structure) | 30, all accepted, each result equal to the expected file |
| Random edits (seed `20261110`) | 1,000 |
| Elements with no clean range, each tried once | 124 (64 with no source position), each refused with its reason |
| **Failures** | **0** |
| html5lib's tree equals parse5's tree | 16 of 16 files; every marked and every spliced document |

The random edits by new HTML:

| New HTML | Edits | Accepted | Refused |
|---|---|---|---|
| (empty) | 139 | 134 | 5 |
| `<p>x</p>` | 152 | 105 | 47 |
| text with CRLF | 141 | 110 | 31 |
| text with U+1F600 | 134 | 103 | 31 |
| `</div><div>` | 132 | 3 | 129 |
| `<!--` | 137 | 0 | 137 |
| `<script>` | 165 | 1 | 164 |

Each accepted edit wrote exactly the bytes before the element, the new HTML and the bytes after it, and the oracle
confirmed that the tree outside the element did not change. Each refusal named its reason, left the file unchanged,
and the oracle confirmed that the splice would change the tree outside. A plain-text edit is refused when the text
would land where the parser moves it, for example directly in a table.

**The 4 accepted listed fragments** (owner's rule: they pass when the oracle confirms the tree outside): `</div><div>`
in place of 2 `option` elements (the parser ignores both tags there), `<script>` in place of an SVG `path` (an SVG
element there), and `</div><div>` in place of an `img` in a table cell. The last one is not one of the owner's two
examples: the `</div>` closes no element in the cell, and the new empty `div` takes the place of the `img`.

**Negative controls** (failures each one causes): moves the node by 1 byte: 466; writes the whole file again from the
tree: 486; changes CRLF to LF: 174; calls every located range clean (extra): 14.

**The oracle's own check:** html5lib passes 1,549 of the 1,792 tree-construction tests of `html5lib-tests` at commit
`9329e64`, fails 180 and skips 63 (fragments in a foreign context). Grouped by the elements in each test's input, the
failures are mostly `template` (100), the `select` rules of 2025 (35) and `ruby` (13). The owner chose to keep html5lib (2026-11-11); the run's parser
comparison found no difference on any document of this run.

**Parser-only rule:** `oracle.py` names no serializer, sanitizer, filter or tree walker; no filter or sanitizer
module was loaded. html5lib's package start loads its serializer and tree-walker modules; the oracle does not call
them.

## C0.2: hostile files

14 hostile files (`tests/gates/hostile.mjs`): text in `pre` and `textarea` that looks like outline lines, the 6 kinds
of hidden content with instructions to the agent, text that becomes markup when an element between two text nodes is
removed, a 100 KB `data:` URI, attribute values with line breaks and both quote kinds, an unclosed comment and an
unclosed script, 513 nested elements, the 2 backtracking inputs, the `html_find` regex case, 10,000 matching
elements, a 1.9 MB file of fostered table rows (extra), and a 25 MB file.

| Condition | Result |
|---|---|
| 1. Each line is an element line or a text line; each ref once, and an element of the oracle with its tag | Held for every outline page and every `html_find` output |
| 2. A `<` from text is `&lt;` | Held |
| 3. Hidden content is not shown, and `html_find` never matches it | Held: 0 matches for each of the 6 hidden words; no hidden element in the outline |
| 4. `html_find` counts, at most 20 matches, empty text refused | Held: 10,000 counted, 20 returned; the regex text counted as literal text (1); the `pre` case equals the oracle's count |
| 5. A long `data:` URI is shortened with its length | Held: `data:…(100022 chars)` |
| 6. The stale-ref case and every path case fail with a named error; no file changes | Held: 6 path kinds × 4 tools, each with its own reason; the UNC and stream cases point at real data |
| 7. Each call ends within 2 s | Held: p50 3 ms, p99 584 ms, max 837 ms |

The slowest cases were all on the 1.9 MB file of fostered table rows: `html_edit` 837 ms, `html_read` 600 ms,
`html_outline` 538 ms, `html_find` 413 ms. Every other case took 75 ms or less.

**Negative controls** (each must fail its named condition): the POC's view of the nested `pre` (c1): fails c1; a
planted backtracking regex (c7): fails c7; `html_find` that reads its text as a regular expression (c4): fails c4; an
`html_find` that matches hidden content (c3): fails c3; an `html_find` with no limit on matches (c4): fails c4.

## What these numbers do not show

- **Timings on an ordinary machine.** The worst case took 837 ms here. A machine 2 times slower would take about
  1.7 s for that edit, and the server stops a call at 1.5 s, which C0.2 counts as a failure. The 1.9 MB worst case is
  an extra file, not one of the contract's cases. Every other case took 75 ms or less.
- **Held-out inputs.** The server's range rule was fixed after development runs on the same inputs and seed. So
  "0 failures" is on inputs that the fix was made against. The contract does not forbid these runs, and the gate
  scripts did not change their inputs after them.
- **Raw outcomes.** The C0.1 result does not save each edit's outcome, and the C0.2 result holds p50, p99, the maximum
  and the 5 slowest cases, not each call's time. Each pass condition shows only as an empty failure list.
- **The percentiles** use the nearest rank (the contract names no method), over calls on files from 100 bytes to
  1.9 MB, so the p50 of 3 ms says little. The server's "2 MB" is 2,097,152 bytes.
- **The extra C0.1 control** changes the first check of the range rule only. Elements that reach the marker parse
  still get it, so the control does not call "every" located range clean, as its amendment says. It still makes C0.1
  fail.
- **Other systems.** Both runs were on Windows only. On Linux and macOS, the link case uses a symbolic link and the
  stream case does not run (`docs/follow-ups.md`).
- **Files outside the set.** C0.1 tested 16 files; html5lib's failures in `template`, `select` and `ruby` could hide a
  defect in a file with those elements. The run's parser comparison found none here.
- **The byte check's range** comes from the server's own view; the marker check confirms it, but cannot see bytes that
  the parser ignores right after an element (`docs/follow-ups.md`).
- **The agents.** These gates test the server. Whether agents use it well, and save tokens, is C0.6.
